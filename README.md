# Laundra 0.3.0 — обновление 16 октября 2026

Готовый проект для существующего приложения Railway. Сначала откройте `UPDATE-OCT16.html`.
Новые переменные окружения не нужны. Обычная команда `npm start` сама применяет добавочную миграцию.

## Что изменилось

- Выплаты можно записывать в любой день, указывать прошлую дату, записывать части и доплаты. Каждая запись — только новая фактически полученная сумма. Ноль означает «пока не получил». Повтор одной отправки не создаёт двойного списания. Нельзя получить больше текущего остатка.
- Половины месяца 1–15 и 16–последний день остаются информационными периодами. Остаток считается по всей истории начислений, расходов и выплат, а не по дате старого периода. Запись задним числом хранит дату получения, но списывает текущий баланс сейчас. История старых подтверждений сохранена отдельно.
- Блок выплат использует карточки сотрудников и истории вместо широкой таблицы. На узких экранах — одна колонка, крупные поля и кнопки.
- Сделка редактируется из карточки: название, клиент, партнёр, ответственный, сумма, оба процента, дата, срок, ожидаемая оплата и следующий шаг. Статус меняется отдельным контролом. Ответственного меняет администратор или пользователь с правом изменения любых сделок. Остальные сохраняют свои права.
- При изменении суммы/процентов завершённой сделки начисляется только разница. Старые записи журнала и фактические выплаты не изменяются. Получатели четырёх долей остаются прежними, в том числе после удаления сотрудника. При уменьшении заработка ниже уже выплаченного баланс может стать отрицательным.
- Фактические платежи можно исправлять и удалять с сохранением аудита. Удаление скрывает платёж из рабочих расчётов, исходная запись остаётся в базе.
- Завершённая сделка считается закрытой независимо от отклонения фактических платежей от плана. Она не попадает в долги и просроченные оплаты. В карточке фактические суммы и отклонение видны для справки. **Расчёт прибыли остаётся по сумме сделки и процентам, а не автоматически по платежам.** Чтобы исправить прибыль, измените сумму или проценты. Обновление само не пересчитывает старую прибыль.
- Аналитика по ответственным: оборот, доля оборота, средняя сделка, число клиентов, завершения, текущая загрузка, ожидания, споры, отмены, просрочки, прибыль, связанные траты, результат, маржа, средний и медианный срок и долги. Пояснения дат и формул видны в интерфейсе; показатели включены в CSV.
- Администратор может удалить и восстановить пользователя. Удаление закрывает вход и завершает прежние сеансы, исключает из будущего распределения дохода. Сделки, авторство, старые доли, баланс и выплаты сохраняются. Главного администратора удалить нельзя. Восстановленный пользователь неактивен до проверки прав администратором.
- Исправлена несовместимость Prisma с возвращаемым типом блокировки при управлении пользователями.

## Обновление без потери истории

1. В Railway откройте сервис **Postgres → Backups** и создайте ручную резервную копию. Дождитесь успешного завершения. [Официальная документация](https://docs.railway.com/volumes/backups).
2. Сохраните текущие значения банков и личных балансов для сравнения. На время обновления попросите команду не редактировать данные.
3. В существующем GitHub-репозитории замените файлы содержимым этого архива. `package.json`, `src`, `prisma` и `scripts` должны остаться в корне репозитория. Не создавайте дополнительную вложенную папку проекта. Сохраните изменения одним коммитом.
4. Дождитесь успешного Railway Deploy. Существующие DATABASE_URL, AUTH_SECRET, ADMIN_PASSWORD и другие Variables оставьте как есть.
5. Обновите страницу приложения. Проверьте банковские остатки и старую историю выплат: сами от установки они меняться не должны. Если есть ошибка, пришлите текст из Deploy Logs; не запускайте сброс базы.

Старые миграции не изменены. Новая миграция `20261016140000_flexible_operations` только добавляет поля и таблицу получений. Она не удаляет и не переписывает старые сделки, платежи, расходы, пользователей, периоды выплат или финансовые записи.

Не используйте `prisma migrate reset`, `db push --accept-data-loss`, не удаляйте Postgres и volume. Старые подтверждения уже вычтены из балансов — не вносите их повторно через новую форму. Пустые старые OPEN-периоды не являются отдельным начислением и не требуют переноса: заработок уже хранится в журнале.

Откат приложения на версию 0.2 после записи новых получений нежелателен: её старый блок подтверждений не рассчитан на новый режим. При проблеме остановите ввод выплат и исправьте/верните код с новой логикой; не откатывайте базу без учёта операций, внесённых после копии.

## Проверки

- `npm test`: 28 регрессионных проверок расчётов, дат, прав, фильтров и аналитики.
- `npm run test:integration`: 11 сценариев в изолированной PostgreSQL (PGlite), включая применение миграции поверх старых данных, позднее получение, доплату, повтор запроса, нулевую запись, запрет переплаты, права, удаление пользователя, исправление завершённой сделки, конфликт редакторов и сохранение выплат.
- `npm run lint`: TypeScript.
- `npm run build`: production-сборка Next.js и генерация Prisma.

Интеграционный тест сам создаёт отдельную тестовую базу и не подключается к DATABASE_URL рабочей системы. PGlite не заменяет проверку конкурентной нагрузки в обычном PostgreSQL. Рабочая база Railway не изменялась при разработке. Вёрстка адаптирована, но реальный iPhone/Safari в этой среде не проверен.

## Для разработчика

Node.js 24, Next.js 16.3.8, PostgreSQL, Prisma 7.10, Auth.js credentials. Финансовые операции используют Serializable-транзакции с повтором конфликтов, блокировками и добавлением корректирующих записей. Редактор сделки проверяет версию updatedAt. Секреты и пользовательские данные в архив не включены.
